# 产品阶段限制草案

状态：`BASELINE / 用户、场景、红线与阶段边界已冻结；证据补齐项持续跟踪`

当前执行限制（2026-10-06）：只开展研究、需求、规则、页面规划和文档工作，不进行代码实现。阶段 B 中的 Web 与 Docker 条目因此属于题目要求与当前限制之间的已知缺口，而非已完成能力。

## 1. 设置限制的目的

限制不是减少产品价值，而是防止每个阶段承担尚未具备证据、技术或运营能力的责任。每阶段同时定义允许范围、禁止范围、进入门槛和退出条件。

## 2. 全阶段不可突破的红线

1. 老人是事务和共享决定的最终主体；
2. 家属参与不能默认变为持续监控；
3. AI 输出未经确认不得触发外部动作；
4. 不宣称提供医疗诊断、应急救援或保证家属响应；
5. 不采集与当前事务无关的数据；
6. 不把 AI 生成内容伪装成用户研究或实测结果；
7. 不把接口隐藏当作安全控制；
8. 不在前端、仓库、镜像或日志保存真实凭据；
9. 不使用真实老人和家庭隐私作为演示数据；
10. 增长、转化和演示便利不得覆盖知情、撤回和删除权。

## 3. 阶段 A：研究与问题定义

### 允许

- 官方资料和厂商资料桌面研究；
- 候选人本人体验相关产品；
- 使用模拟角色检查流程逻辑；
- 形成假设、反例和验证计划。

### 限制

- 不把桌面研究写成用户体验；
- 不把一位熟人意见外推为老年群体结论；
- 不把产品公开功能等同于易用或有效；
- 不先决定技术再倒推用户问题；
- 不进入医疗、紧急、金融和持续定位场景。

### 进入下一阶段门槛

- 目标老人和家庭条件可用一句话描述；
- 主要问题只有一个；
- 两个本人文字体验记录完成；严格证据包仍需补截图、录屏和精确版本；
- 事实、分析和假设已分开；
- 必做与不做范围已签字式确认。

### 退出/转向条件

- 现有工具加简单教学即可同等解决；
- 用户问题主要需要线下服务而非软件；
- 价值依赖医疗或应急承诺；
- 家庭权力关系使老人无法真实同意。

## 4. 阶段 B：考核演示原型

### 允许

- 固定案例和预设模拟状态；
- 静态 SPA、本地状态、虚构账号；
- 演示控制器切换角色；
- 模拟语音、AI、消息、等待和失败；
- 一个老人、一名主要家属、一个事务类型。

### 功能限制

- P0 需求全部覆盖后才做 P1；
- 导航最多保留实际可完成的入口；
- 不支持任意自然语言或任意事务；
- 不做群组协作、机构后台和完整历史；
- 不做真实登录、注册、支付和消息。

### AI 限制

- 仅返回结构化 fixture；
- 不读取历史、位置、通讯录和健康数据；
- 不给专业建议；
- 不自动创建、发送、改期或取消；
- 页面和演示说明明确“模拟 AI”。

### 数据限制

- 只用虚构姓名、关系和事务；
- 默认内存或 `sessionStorage`；
- 不产生真实用户画像和行为跟踪；
- 只记录测试用例结果，不记录私人输入。

### 技术限制

- 单容器静态服务；
- 无数据库、后端、外部 API 和秘密；
- 不为了“像真实产品”引入不必要基础设施；
- 演示工具和业务 UI 视觉隔离；
- Docker 无公网仍能完成验收。

### 时间和成本限制

- 研究与范围在开发前冻结；
- 开发总预算不超过 42 人时；
- 最后至少留 4 小时全量走查；
- 新需求必须替换同等工作量，不允许只增加。

### 进入提交门槛

- 题目要求全部映射到页面或文档；
- 主流程、修改/取消、失败、未回应和跨角色流程走通；
- 静态图与 Web 同版本；
- Docker 在干净环境启动；
- 无秘密、真实数据、空按钮和断路由；
- 页面清单可定位每个状态。

## 5. 阶段 C：可用性验证

### 允许

- 5 组左右目标老人—家属配对；
- 使用虚构或低敏日常事务；
- 观察理解、纠错、授权和回应；
- 记录操作、求助、误解和中止。

### 研究限制

- 不诱导参与者说“好用”；
- 不由研究员代替老人完成关键操作；
- 不把家属意见替代老人意见；
- 不采集身份证、病历、银行卡、精确位置和真实账户；
- 不把小样本结果写成市场规模结论；
- 不把目标值写成实测值。

### 安全限制

- 原型仍不发送真实消息；
- 不存储原始语音；
- 参与者可随时退出并删除记录；
- 录像、截图和引用需单独同意；
- 报告去标识化。

### 进入下一阶段门槛

- 主要用户能理解系统确认页；
- 预设错误可被发现并修正；
- 多数参与者能解释共享给谁、共享什么；
- 家属能快速理解行动要求；
- 未回应和取消不会产生严重误判；
- 已确认独立产品相对现有替代方案的增量价值。

## 6. 阶段 D：封闭技术试点

### 允许

- 受邀家庭、明确地区和支持时间；
- 真实认证、最小后端、App 内通知；
- 可替换 AI 理解适配器；
- 有限真实事务，但继续排除敏感领域。

### 用户限制

- 只面向能自主作出决定的老人；
- 一户默认一名主要家属；
- 不面向需要医疗监护或认知障碍专业照护的人群；
- 不承诺 7×24 小时人工响应。

### 数据限制

- 完成个人信息影响评估；
- 字段级目的、保留期和共享方清楚；
- 原始语音默认不保存；
- 不采集持续位置、病史和金融账户；
- 撤回关系后立即阻止新访问；
- 数据导出和删除路径可用。

### 接口限制

- 前端只访问同源 BFF；
- 服务端逐对象和逐字段授权；
- 管理、调试和 API 文档不公开；
- 凭据仅运行时注入；
- 限速、幂等、审计和异常告警生效；
- 未完成跨家庭授权测试不得上线。

### AI 限制

- 使用固定 schema 和允许字段；
- 低置信或缺失字段必须请求确认；
- 供应商失败回退手动输入；
- 不将家庭数据默认用于训练；
- 供应商更换不改变核心状态和权限。

### 运营限制

- 明确服务时间、故障通知和投诉入口；
- 不将未回应升级为恐吓式提醒；
- 家属提醒频率有上限；
- 社区或渠道人员不能代同意；
- 严重误导、跨家庭访问或假成功触发暂停试点。

## 7. 阶段 E：渠道与规模化

### 扩展前门槛

- 14 日复用和端到端成功有真实数据；
- 每家庭获客、配置、客服和渠道成本可解释；
- 有稳定的删除、投诉、审计和事故响应机制；
- 核心权限和适老组件自动化测试通过；
- 至少一条渠道不依赖高成本人工代操作。

### 扩展限制

- 一次只增加一个事务类型或一个渠道；
- 新角色必须重新做权限矩阵和威胁建模；
- 接入位置、健康、支付前必须单独立项，不沿用普通事务同意；
- 不用留存或转化理由扩大默认共享；
- 不让渠道合作方默认成为数据接收者；
- 不把外部平台能力当作不可替代的核心状态存储。

## 8. 各维度总限制表

| 维度 | 原型 | 验证 | 试点 | 规模化前要求 |
|---|---|---|---|---|
| 用户 | 固定虚构角色 | 约 5 组目标家庭 | 受邀、能自主决策 | 分层画像与排除标准 |
| 场景 | 一个日常事务 | 同一事务 | 有限真实事务 | 一次扩一类 |
| 家属 | 一名主要家属 | 一对一 | 默认一名 | 新角色重做权限 |
| AI | fixture | fixture/向导 | 受约束真实适配器 | 评估、监控、供应商退出 |
| 消息 | 模拟 | 模拟 | App 内优先 | 渠道 SLA 与成本 |
| 数据 | 虚构、本地 | 去标识研究记录 | 最小真实数据 | 全生命周期治理 |
| 权限 | 规则演示 | 理解验证 | 服务端强制 | 自动化安全测试 |
| 医疗/应急 | 禁止 | 禁止 | 禁止 | 单独资质与责任项目 |
| 成本 | 0 外部服务 | 低成本研究 | 月度预算封顶 | 单家庭单位经济模型 |
| 指标 | 定义口径 | 可用性 | 复用、成功、风险 | 留存、成本、事故率 |

## 9. 需求变更限制

任何新增需求必须回答：

1. 它解决哪个已验证问题；
2. 属于哪个角色和状态；
3. 新增哪些页面、异常、权限和测试；
4. 需要采集什么数据；
5. 会替换哪个现有工作项；
6. 如果不做，当前核心闭环是否仍成立。

无法回答或只增加演示效果的需求，不进入当前版本。
