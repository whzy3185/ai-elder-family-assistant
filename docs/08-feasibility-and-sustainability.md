# 可实现性与可延续性

## 1. 分阶段可行性

| 阶段 | 可行性 | 理由 |
|---|---|---|
| 48 小时演示原型 | 高 | 无后端、无真实 AI/消息；有限状态和固定案例 |
| 5—10 组家庭可用性测试 | 高 | 使用虚构任务；主要验证理解和协作规则 |
| 100 个家庭封闭试点 | 中 | 需要认证、消息、隐私、客服和稳定性 |
| 开放消费产品 | 中低 | 获客、留存、责任边界和持续运营尚未验证 |
| 医疗/应急场景 | 低且不纳入 | 需要专业资质、SLA、责任与更强安全保障 |

## 2. 核心可行性依据

- 人口与数字化基础足够大，但差异明显，支持聚焦细分人群；
- 提醒、语音、家庭共享和消息都是成熟基础能力；
- 题目允许使用预设状态，无需真实服务；
- 领域对象数量有限：用户、关系、事务、请求、回应和同意；
- 可用确定性状态机覆盖验收脚本。

## 3. 当前最大未知

1. 老人是否愿意安装独立产品，还是必须嵌入现有平台；
2. 老人是否能理解“事务”和“请求”两个状态；
3. 家属是否认为请求足够具体且不造成负担；
4. 未回应时怎样处理最不制造焦虑；
5. 家属、老人或机构中谁愿意付费；
6. 双方关系紧张时，授权和撤回是否仍能被尊重。

这些未知不能靠增加功能解决，应通过小样本走查和封闭试点验证。

## 4. 可延续的领域模型

稳定核心：

- `Task`：老人自己的事务；
- `Relationship`：经双方确认的协作关系；
- `ConsentGrant`：关系或单次共享授权；
- `AssistanceRequest`：针对一件事务向一名家属发出的请求；
- `Response`：接受、拒绝或建议修改；
- `DomainEvent`：状态变化和审计记录。

可替换外部适配器：

- `UnderstandingAdapter`：规则、云模型或端侧模型；
- `NotificationAdapter`：App 内、短信、微信或设备推送；
- `IdentityAdapter`：手机号、平台账号或机构账号；
- `CalendarAdapter`：系统日历或第三方日历。

这样可以更换供应商而不改写核心权限和状态规则。

## 5. 产品延续条件

进入下一阶段前至少满足：

- 目标用户能独立走通主流程；
- 家属端回应时间和负担可接受；
- 用户理解共享范围且能撤回；
- 第二件事务复用率达到预设验证阈值；
- 未发现严重状态误判；
- 无跨家庭数据访问；
- 有一条可重复的获客与首次配置路径；
- 单家庭服务成本有可持续假设。

## 6. 退出或转向条件

- 老人持续依赖家属代操作，产品没有提升自主性；
- 家属把产品主要用于监控而非协作；
- 单次任务价值不足以形成复用；
- 用户只能通过高成本线下服务完成每次使用；
- 合规与责任成本显著超过场景价值；
- 现有日历/通讯工具通过简单教学即可同等解决问题。

若出现上述情况，应转向为现有平台提供适老协作组件或社区服务工具，而不是继续建设独立消费 App。

## 7. 可持续性原则

- 商业持续性：先验证家庭复用，再讨论订阅或机构采购；
- 技术持续性：标准领域模型 + 供应商适配器；
- 运营持续性：让首次配置可由家庭和社区完成，减少长期人工代办；
- 伦理持续性：不以持续监控或数据交易作为商业模式；
- 无障碍持续性：组件基线和自动检查进入每次发布门槛。
