# 项目需求框架草案

状态：`BASELINE / 核心用户、场景与范围已冻结；其余规则按决策台账继续收敛`

当前执行限制（2026-10-06）：候选人要求不做代码实现。本文仍按题目完整验收要求定义产品需求，但 Web 原型、运行态交互和 Docker 相关需求目前只能保留为未实现的交付缺口。

## 1. 题目本质

题目不是要求建设“养老平台”，而是考察能否围绕一个具体老人和家庭条件，完成一次具有 AI 理解、老人确认、家庭协作、权限边界和异常恢复的事务闭环。

评分对象实际分为六层：

1. **需求判断**：是否选择了真实、具体、值得解决的问题；
2. **范围取舍**：是否在 48 小时内做完一个闭环，而非堆叠功能；
3. **交互完整性**：双方页面、关键状态和跳转是否真实存在；
4. **业务规则**：老人、家属和 AI 的权利、责任和状态是否一致；
5. **证据与验证**：事实、体验、假设和指标是否可追溯；
6. **交付可靠性**：源码、静态原型、Docker、README 和走查是否同版本。

## 2. 隐含冲突与解法

| 题目要求中的冲突 | 常见错误 | 本项目解法 |
|---|---|---|
| 页面完整，但时间只有 48 小时 | 画很多入口，后续页面为空 | 只保留一个事务类型和一名家属协作者 |
| AI 要体现价值，但不能真实接入 | 做不可控聊天框或假装真实模型 | 固定输入案例 + 结构化解析适配器 + 明示模拟 |
| 家属适度参与，但不能默认监控 | 家属能看全部历史、位置和资料 | 每次请求单独确认最小共享字段 |
| 可以从已登录开始，但首次协作必须覆盖 | 完全跳过关系建立 | 只省略账号注册，保留双方关系确认 |
| 可角色切换演示，但真实产品不能越权 | 把角色切换放入真实导航 | 使用独立、显式标注的演示控制栏 |
| 需要异常完整，但不应机械复制 | 每页复制全部空/错/成功状态 | 只为真实流程节点设计相关状态 |
| 需要研究依据，但不强制真人访谈 | 生成虚假访谈 | 公开资料 + 本人体验 + 明示假设 |

## 3. 产品章程

### 3.1 已冻结产品主张

帮助 72 岁、具备自主决策能力、会使用智能手机基础功能、独居或日间独处的张阿姨，把一句自然语言需求整理成可确认的日常事务，并在她主动选择时，请同城但工作繁忙的女儿小梅给予明确回应。

### 3.2 已冻结固定案例

> “明天上午九点去社区服务中心办公交卡年审，提前半小时提醒我，再问问小梅能不能陪我去。”

预设 AI 将 9:00 错误理解为 8:00，提前 30 分钟的提醒因此先显示为 7:30。老人把事务时间纠正为 9:00 后，提醒同步更新为 8:30；随后再决定是否向小梅发送陪同请求。

### 3.3 已确认的使用条件

- 张阿姨 72 岁，具备自主决策能力，会微信语音、扫码和基础手机操作；
- 独居或日间独处，不以疾病或失能标签定义用户；
- 小梅是同城女儿，工作忙，可以查看请求但不能保证陪同；
- 当前事务固定为社区服务中心公交卡年审，所需帮助是陪同而非代办；
- 首版只有一名家属协作者，不设置第二联系人；
- 小梅未回应时，张阿姨可继续等待、撤回陪同请求或自行安排；个人提醒保持有效。

## 4. 角色与目标

### R1 老人

- 目标：表达事务、检查系统理解、修正错误、决定是否请求家属、获得明确结果；
- 权利：拥有事务、决定共享、接受或拒绝家属改期、取消请求、撤回关系；
- 限制：不要求理解技术术语、权限模型或复杂设置。

### R2 指定家属

- 目标：快速理解老人需要什么，在自己的能力范围内明确回应；
- 权利：接受、拒绝、建议改期；
- 限制：不能直接修改或删除老人事务，不能浏览未授权事务和完整历史。

### R3 AI 理解服务

- 目标：把老人输入整理为事项、日期、时间、地点、协作意图；
- 权利：仅生成待确认结果；
- 限制：不能自动发送、自动修改、作医疗判断或声称家属已经回应。

### R4 演示控制器

- 目标：帮助评审切换角色、加载状态和恢复初始数据；
- 限制：只存在于演示环境，不属于真实产品功能，不得与业务权限混淆。

## 5. 核心领域对象

| 对象 | 关键字段 | 所有者/可见者 |
|---|---|---|
| `Person` | id、称呼、角色、适老偏好 | 本人；关系建立后可见最小资料 |
| `Relationship` | 双方、状态、创建时间、撤回时间 | 关系双方 |
| `Task` | 事项、日期、时间、地点、备注、状态、版本 | 老人；按请求授权给家属部分字段 |
| `ConsentGrant` | 接收者、字段范围、目的、时间、状态 | 老人与审计逻辑；家属看可共享范围说明 |
| `AssistanceRequest` | taskId、接收者、问题、状态、期限 | 双方 |
| `Response` | 接受/拒绝/建议改期、说明、时间 | 双方 |
| `UnderstandingResult` | 原始输入引用、结构化字段、置信/待确认标记 | 老人；确认前不共享 |
| `DomainEvent` | 对象、动作、角色、时间、原因 | 原型内部；真实产品受控审计 |

## 6. 权限矩阵

| 能力 | 老人 | 指定家属 | AI | 演示控制器 |
|---|---:|---:|---:|---:|
| 创建事务 | 允许 | 禁止 | 仅建议 | 加载预设 |
| 修改事务 | 允许 | 禁止 | 仅建议 | 加载预设 |
| 发出协作请求 | 明确确认后允许 | 禁止 | 禁止 | 加载预设 |
| 查看共享事务字段 | 全部 | 仅授权字段 | 仅处理所需字段 | 虚构数据 |
| 接受/拒绝 | 不适用 | 允许 | 禁止 | 加载预设 |
| 建议改期 | 最终确认 | 允许提出 | 禁止 | 加载预设 |
| 取消请求 | 允许 | 不允许代取消 | 禁止 | 加载预设 |
| 撤回关系 | 允许 | 允许退出 | 禁止 | 重置数据 |
| 查看位置/病史/其他日程 | 本版本不采集 | 禁止 | 禁止 | 禁止 |

## 7. 需求层级

### 7.1 P0：必须完成

#### FR-01 首次协作关系确认

- 从预置登录状态进入；
- 一方发起与指定家属建立协作；
- 老人端清楚看到对方、用途和权限；
- 老人可同意或拒绝；
- 双方可查看当前关系；
- 至少老人端可取消关系。

#### FR-02 表达日常事务

- 支持预设语音模拟和手动文字入口；
- 输入期间说明录音/模拟状态；
- 无法识别时保留已有内容并提供手动填写。

#### FR-03 AI 结构化理解

- 展示事项、日期、时间、地点和协作意图；
- 不确定或错误字段可单独修改；
- 确认前不创建正式事务、不通知家属。

#### FR-04 创建和查看事务

- 老人确认后创建事务；
- 事务详情展示当前状态和下一步；
- 老人可返回修改或取消；
- 修改后所有后续示例内容保持一致。

#### FR-05 单次协作授权

- 老人选择是否请求家属；
- 展示接收者和本次共享字段；
- 默认不共享位置轨迹、历史或其他事务；
- 老人确认后才发送。

#### FR-06 家属回应

- 家属看到请求列表与详情；
- 可接受、拒绝或建议改期；
- 操作后显示提交结果；
- 不能操作已取消或过期请求。

#### FR-07 老人获知结果

- 老人看到家属回应和事务当前状态；
- 改期建议必须由老人接受或拒绝；
- 结果文案说明下一步。

#### FR-08 取消

- 老人可取消尚未终结的请求；
- 双方同步显示已取消；
- 家属后续操作被拒绝且解释原因。

#### FR-09 未回应

- 请求超过演示期限进入未回应/已过期；
- 老人知道家属尚未回应，而不是已拒绝；
- 提供待确认的替代动作：继续等待、再次提醒、取消或选择其他安排。

#### FR-10 失败和重试

- 至少覆盖 AI 无法理解、请求发送失败之一；
- 失败不显示成功、不丢失输入；
- 提供明确重试或手动替代路径。

#### FR-11 演示控制

- 角色切换、案例加载、异常状态和一键重置；
- 明确标记“演示工具”；
- 不出现在生产构建约束中。

### 7.2 P1：有余量才做

- 第二联系人，但只允许串行选择，不做群组协作；
- 已完成事务的只读历史；
- 家属端补充一句回应说明；
- 字号偏好和高对比切换；
- App 内二次提醒，但有频率上限。

### 7.3 P2：本次明确不做

真实语音识别、真实大模型、真实通知、位置、支付、医疗、应急、硬件、智能家居、多人群聊、机构后台、开放式陪聊、任意事务泛化。

## 8. 状态模型

### 8.1 事务

```text
DRAFT
  -> UNDERSTANDING
  -> NEEDS_CONFIRMATION
  -> CONFIRMED
  -> COMPLETED
  -> CANCELLED
```

### 8.2 协作请求

```text
NOT_REQUESTED
  -> CONSENT_REQUIRED
  -> SENDING
  -> DELIVERED
  -> VIEWED
  -> ACCEPTED | DECLINED | CHANGE_PROPOSED | EXPIRED
  -> CANCELLED
```

### 8.3 不变量

- `SENDING` 不能显示“家属已收到”；
- `DELIVERED` 不能显示“家属已查看”；
- `VIEWED` 不能显示“家属已同意”；
- `CHANGE_PROPOSED` 不直接改变 `Task`；
- `CANCELLED` 和 `EXPIRED` 不接受新回应；
- 事务取消会终止所有未终结请求；
- 任意角色看到的状态语义必须一致。

## 9. 页面族框架

最终页面清单需在范围冻结后逐项编号。本框架至少包含：

### 老人端

1. 首页/事务入口；
2. 首次关系邀请与权限说明；
3. 表达事务；
4. AI 处理中；
5. 理解确认；
6. 字段修改；
7. 事务详情；
8. 请求家属与共享确认；
9. 发送中/发送失败；
10. 等待回应；
11. 接受/拒绝/改期结果；
12. 未回应；
13. 取消确认与取消结果。

### 家属端

1. 首次关系请求；
2. 请求列表/空状态；
3. 请求详情；
4. 接受结果；
5. 拒绝确认与结果；
6. 建议改期；
7. 请求已取消或已过期。

### 演示层

1. 角色切换；
2. 场景状态选择；
3. 恢复初始数据；
4. 当前状态说明。

页面是否合并取决于操作复杂度，但任何被合并的关键状态仍需可定位、可截图和可独立进入。

## 10. 非功能需求

### NFR-01 适老与无障碍

- 老人端正文建议 20 px 起；
- 普通文本对比度不低于 4.5:1；
- 控件建议不小于 48 × 48 CSS px；
- 支持 200% 缩放、键盘和合理焦点顺序；
- 不只用颜色表达状态；
- 一屏一个主操作。

### NFR-02 性能与可靠性

- Docker 启动后首页本地加载不依赖公网；
- 操作反馈即时；模拟等待应可跳过或短于 2 秒；
- 刷新后的行为在 README 中明确；
- 一键重置恢复统一初始状态。

### NFR-03 安全与隐私

- 无真实个人数据、密钥和外部 API；
- 演示工具不进入未来生产构建；
- 共享字段可见且最小；
- 错误不暴露内部实现；
- 构建产物不包含调试页面、source map 或测试凭据。

### NFR-04 一致性

- 产品文档、页面清单、静态图、Web、测试和演示说明使用同一状态名称；
- 固定案例修改后，所有后续字段同步变化；
- 每个页面和状态拥有唯一编号。

## 11. AI 契约

### 输入

- 当前一次用户输入；
- 用户明确提供的日期、时间、地点和协作对象；
- 本版本不读取历史记忆、通讯录、位置或健康信息。

### 输出

- `title`、`date`、`time`、`location`、`assistanceIntent`；
- 每个字段的 `confirmed/needsConfirmation` 状态；
- 无法理解时返回明确失败，不编造缺失字段。

### 页面行为

- 输出始终先进入确认页面；
- 错误可以逐字段修改；
- 确认后才生成 `Task`；
- 失败时切换手动表单并保留原输入。

## 13. 需求冻结门槛

以下问题没有答案前，不进入高保真视觉和完整开发：

- 具体老人和家庭条件；
- 唯一主要事务；
- 老人与家属的权力边界；
- 未回应后的替代动作；
- 是否允许第二联系人；
- 固定演示错误与失败类型；
- 两个本人体验样本；
- P0 页面族无遗漏。
