# 产品章程：AI 日常事务与家庭协作助手

版本：`PRODUCT_CHARTER_VERSION=1.0.0`

冻结日期：2026-10-06（Asia/Shanghai）

状态：`PASS / 阶段 01 Gate`

本章程是后续需求、页面、Web、测试、截图、README 和演示说明的产品范围基线。除非出现新的直接证据并记录变更原因、影响范围和迁移方案，否则不得更换核心事务。

## 1. 一句话产品定义

帮助具备自主决策能力、会使用智能手机基础功能但不喜欢复杂操作的老人，把一句日常办事需求整理成可检查、可纠错、可提醒的个人事务，并在老人逐次明确授权后，向一名指定家属提出有限的协作请求并获得清楚结果。

## 2. 用户画像

### 2.1 老人：张阿姨

| 项目 | 冻结内容 |
|---|---|
| 年龄 | 72 岁 |
| 居住 | 独居或日间独处 |
| 自主能力 | 具备自主决策和正常行为能力 |
| 常用设备 | 智能手机；本考核使用 390 × 844 移动 Web 模拟 |
| 已会操作 | 微信语音、扫码、接电话、基础智能手机操作 |
| 操作特点 | 不喜欢复杂表单、多层菜单、精细手势和含义模糊的反馈 |
| 适老需求 | 较大文字与按钮、少步骤、明确反馈、可纠错、手动替代入口 |
| 明确不是 | 需要认知障碍照护、法定监护或全权托管的用户 |

“操作手机不熟练”不得被解释为“缺乏自主行为能力”。

### 2.2 家属：小梅

| 项目 | 冻结内容 |
|---|---|
| 关系 | 张阿姨的成年女儿 |
| 距离 | 同城 |
| 时间条件 | 平时工作较忙 |
| 可参与程度 | 可以查看具体请求并回应，但不能保证陪同 |
| 产品角色 | 一次事务的受邀协助者，不是事务所有者或老人管理者 |
| 明确权限 | 接受、拒绝或建议改期 |
| 明确禁止 | 直接修改、取消或完成张阿姨的事务；查看未授权信息 |

## 3. 家庭条件

- 当前只有张阿姨与小梅两名业务角色；
- 首次关系由小梅扫码发起，张阿姨查看身份、用途、可见范围和撤回方式后决定同意或拒绝；
- 关系建立只代表双方可以进行协作，不代表小梅自动获得张阿姨的位置、历史、完整日程或全部事务；
- 每一件事务是否共享、共享给谁、共享哪些字段，仍由张阿姨单独确认；
- 小梅未回应不等于拒绝，更不等于已经接受；
- 张阿姨拒绝关系或拒绝本次共享后，个人事务和个人提醒仍可正常保存。

## 4. 唯一核心事务

张阿姨计划第二天上午 9:00 去社区服务中心办理一次老年公交卡年审，希望手机提前 30 分钟提醒，并询问小梅能否陪同。

### 4.1 固定示例语音

> “明天上午九点去社区服务中心办公交卡年审，提前半小时提醒我，再问问小梅能不能陪我去。”

### 4.2 事务边界

产品只记录和协作这件事，不提供年审政策、资格、材料、费用、网点真实性或办理结果判断。演示中的“社区服务中心”是虚构地点名称，不代表真实政务机构。

## 5. 触发场景

张阿姨在晚上想到第二天要办理公交卡年审。她希望避免忘记时间，但又不想填写复杂表单；同时她愿意让小梅知道这件事并询问能否陪同，却不希望因此开放其他生活信息。

触发条件同时满足：

1. 存在一件明确、低风险的日常外出事务；
2. 老人需要个人提醒；
3. 家属协助是可选项，不是事务成立的前提；
4. 家属不能保证响应；
5. 事务不涉及医疗、应急、支付、位置监控或专业政务建议。

## 6. 用户目标

### 6.1 张阿姨的目标

1. 用自然语言表达一次事务；
2. 知道系统具体理解了什么；
3. 发现并只修改错误字段；
4. 保存正确的个人事务和提醒；
5. 自己决定是否邀请小梅；
6. 发送前知道小梅将看到什么；
7. 得到“接受、拒绝、建议改期、暂未回应”等明确结果；
8. 可以撤回请求或取消自己的事务；
9. 最终由自己确认事务是否办完。

### 6.2 小梅的目标

1. 快速知道妈妈要办什么、何时、何地、希望自己做什么；
2. 在不接管妈妈事务的前提下快速回应；
3. 可以诚实拒绝或提出新时间；
4. 不因建立关系而承担持续监控和无限响应责任；
5. 不再操作已经撤回、取消、过期或被新版本替代的旧请求。

## 7. 双方可能冲突

| 冲突 | 产品处理 |
|---|---|
| 张阿姨希望少步骤，但共享必须知情 | 个人事务先保存；共享作为第二个独立动作，并用一屏最小字段确认 |
| 小梅希望信息充分，但张阿姨希望隐私最小 | 只共享事项、日期、时间、地点和所需帮助 |
| 张阿姨期待陪同，但小梅不能保证时间 | 明确接受、拒绝、建议改期和暂未回应，不暗示保证 |
| 小梅希望直接改时间更省事，但事务属于张阿姨 | 小梅只能提出改期，张阿姨确认后才生效 |
| 张阿姨修改已发送事务，但小梅可能仍在旧页面 | 作废旧请求并生成新版本；旧答复被明确拒绝 |
| 家属担心安全，希望看到更多信息 | 本产品拒绝用“安全”扩大默认权限，不提供位置或持续监控 |

## 8. 核心问题

现有提醒工具善于保存任务，聊天工具善于发送消息，家庭守护工具善于建立持续关系；但它们容易缺少以下组合：

> 老人先纠正系统理解，先保存自己的事务，再逐次确认最小共享；家属只回应一次有限请求，双方始终知道当前状态和下一步。

本产品的核心不是“AI 聊天”，而是可纠错、可撤回、权责清楚的个人事务与家庭协作闭环。

## 9. P0：本次必须交付

P0 中的每项都必须出现在需求矩阵、页面矩阵、静态画面、Web、测试和演示说明中。

### 9.1 关系与权限

- 小梅模拟扫码发起关系；
- 张阿姨查看对方身份、用途、可见范围和撤回方式；
- 张阿姨同意或拒绝建立关系；
- 关系已建立状态；
- 张阿姨可结束关系；
- 关系建立不自动开放任何事务。

### 9.2 事务理解与个人提醒

- 模拟语音输入和手动文字替代；
- AI 处理中；
- 结构化展示事项、日期、时间、地点、提前提醒和协作意图；
- 固定识别错误 9:00→8:00；
- 单字段把 8:00 改回 9:00；
- 提醒时间从 7:30 联动为 8:30；
- 必要信息缺失；
- AI 解析失败并保留输入、回退手动表单；
- 张阿姨确认并保存个人事务；
- 事务详情；
- 个人提醒保存；
- 提醒触发；
- 张阿姨确认事务完成。

### 9.3 单次家庭协作

- 张阿姨选择只提醒自己、不共享；
- 张阿姨选择请求小梅陪同；
- 发送前展示本次共享字段；
- 张阿姨明确确认发送；
- 发送中；
- 发送失败并由用户主动重试；
- 小梅的请求列表、空状态和请求详情；
- 小梅接受、拒绝或建议改期；
- 张阿姨看到回应；
- 改期建议由张阿姨接受或拒绝；
- 小梅未回应时，张阿姨可继续等待、撤回请求或自行安排；
- 张阿姨撤回陪同请求但保留个人事务与提醒；
- 张阿姨取消整个事务并终止未完成请求；
- 已发送后修改事务时作废旧请求并生成新版本；
- 旧请求和旧家属答复失效。

### 9.4 演示与可复现性

- 显式标注的角色切换和 Demo Controller；
- 主流程与全部 P0 异常可直接加载；
- 一键恢复固定初始状态；
- 所有业务数据均为虚构数据；
- 无真实 AI、消息、语音、账号、数据库或外部服务；
- Docker 离线启动后可以连续操作。

## 10. P1：不阻塞交付的增强项

P1 只有在全部 P0 已通过后才能进入；任一 P1 不得在导航中以空入口出现。

- “标准 / 大字”显示切换；默认模式本身已满足适老基线；
- 高对比显示切换；
- 小梅在接受、拒绝或建议改期时附加一条可选短说明。

若时间不足，全部 P1 直接删除，不影响产品闭环和最终验收。

## 11. Explicitly Excluded

以下内容不属于本次产品能力，不设计空入口，不以 Roadmap 文案伪装为当前可用：

- 公交卡年审政策、材料清单、办理资格、费用、网点真实性和政务解释；
- 医疗诊断、病情判断、用药、陪诊和健康数据；
- 应急救援、110/120、跌倒检测和安全保证；
- 实时位置、位置轨迹、摄像头、环境音和持续监控；
- 智能家居、可穿戴设备和专用硬件；
- 开放式陪聊、情绪治疗和通用问答；
- 支付、银行卡、保险、代购和打车；
- 多家属并发、家庭群、第二联系人和自动升级联系人；
- 法定监护、代理核验和全权托管；
- 真实短信、电话、推送、微信接口或系统日历写入；
- 真实 AI、真实语音识别和任意自然语言泛化；
- 后端、数据库、真实登录注册和账号恢复；
- 完整历史中心、机构后台、运营后台和管理后台；
- 真实个人信息、真实家庭关系和真实政务数据。

## 12. 冻结权限原则

1. 张阿姨拥有自己的事务；
2. 张阿姨决定是否共享；
3. 张阿姨决定共享给谁、共享什么；
4. 小梅不能直接修改、取消或完成张阿姨的事务；
5. 小梅只能针对当前有效请求接受、拒绝或建议改期；
6. 改期建议必须经张阿姨再次确认；
7. 关系授权和单次事务授权是两个独立授权；
8. 一次共享不构成持续共享；
9. 未回应不是拒绝，送达不是查看，查看不是接受；
10. 已撤回、取消、过期或旧版本请求不可继续操作；
11. 不熟悉手机不等于缺乏自主行为能力；
12. 当前只实现自主模式。

### 12.1 本次共享字段

小梅只看到：

- 事项：办理老年公交卡年审；
- 日期：2026-10-07；
- 时间：09:00；
- 地点：社区服务中心；
- 所需帮助：希望小梅陪同。

小梅不看到个人提醒时间、输入原文、AI 识别过程、备注、位置、其他事务或历史。

## 14. 为什么选择该唯一事务

1. **覆盖题目完整能力**：一次流程同时包含自然语言理解、纠错、提醒、授权、双端协作和异常；
2. **日常且低风险**：不需要医疗、支付、定位或应急承诺；
3. **家属参与合理但非必需**：陪同有价值，但小梅拒绝或未回应时事务仍成立；
4. **字段明确**：事项、日期、时间、地点和帮助类型适合结构化确认；
5. **适合演示错误**：时间识别错误会联动提醒时间，能真实体现纠错价值；
6. **权限边界清楚**：小梅只需知道本次办事信息，无需查看其他隐私；
7. **与竞品研究一致**：吸收 Apple 的结构化提醒和华为的双边确认，同时避免共同编辑和持续守护权限过宽。

## 15. 为什么不继续扩展

- 每增加一个事务类型都会增加字段、异常、文案、页面和测试组合；
- 每增加一个家属都会引入并发回应、冲突、优先级和隐私问题；
- 政务、医疗、支付、位置和应急都会引入本考核不需要的真实性与责任风险；
- 开放式 AI 会降低演示可复现性并增加错误面；
- 完整历史、后台和账号体系不能提升本次核心闭环的判断质量；
- 48 小时考核更重视一个连续、规则一致、可验证的流程，而不是功能数量。

## 16. 范围变更规则

核心用户、核心事务、演示时钟、共享字段、权限原则和 Explicitly Excluded 自本版本起冻结。变更必须同时满足：

1. 有新证据证明当前选择无法满足题目或存在重大风险；
2. 写明替代内容、原因和影响页面；
3. 同步更新需求矩阵、页面矩阵、状态机、fixture、测试、截图、README 和演示说明；
4. 不得在单个文件中静默更改固定时间或示例文案。

## 17. 指令版本说明

此前“不做代码实现”是研究阶段的阶段性约束。自用户要求“按照任务链从 阶段 00 开始并继续推进”起，执行边界改为：

- 阶段 00—06 按各阶段要求完成研究、规则和设计；
- 阶段 07 起允许并要求建立 Web 原型；
- 阶段 11 起允许并要求完成 Docker；
- 当前 阶段 01 仍然不写代码、不画 UI。

因此，旧审计中“全程不编码导致无法完整交付”的判断保留为历史记录，但不再是后续任务链的现行阻碍。
