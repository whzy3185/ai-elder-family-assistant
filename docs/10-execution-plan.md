# 执行 Plan

## 1. 分支策略

- `main`：经过验收、可提交的稳定版本；
- `research`：市场、用户、规则、安全、可行性和计划；
- `feat/prototype`：Web 原型与测试；
- `docs/product-delivery`：产品说明、页面清单、走查和演示说明。

采用短分支和小提交，不在 48 小时项目中引入复杂 Git Flow。

## 2. 48 小时工作分解

| 时间 | 工作 | 输出 | 验收 |
|---|---|---|---|
| 0—4h | 题目拆解与范围冻结 | 用户、场景、边界、假设 | 一句话能解释产品 |
| 4—8h | 两个产品本人体验 | 证据记录与设计影响 | 有步骤、截图和事实/判断区分 |
| 8—12h | 领域规则与页面状态 | 状态机、双端权限、页面清单 | 验收脚本无断点 |
| 12—18h | 信息架构与视觉基线 | 流程图、组件和关键页面 | 字号、对比、按钮、文案通过检查 |
| 18—30h | 原型开发 | 主流程、角色切换、修改 | 从入口到回应结果可操作 |
| 30—36h | 异常与双端一致 | 取消、拒绝、未回应、失败 | 状态同步，无假成功 |
| 36—40h | 静态原型与产品文档 | 完整画面、规则、指标 | 编号一一对应 |
| 40—44h | Docker 与自动检查 | Compose、README、测试 | 干净环境可启动 |
| 44—47h | 全量走查与修复 | 走查记录、已知问题 | 四条路径完成 |
| 47—48h | 冻结和提交 | 最终 SHA、材料准备 | 仓库与材料版本一致 |

## 4. 已冻结固定演示案例

老人说：“明天上午九点去社区服务中心办公交卡年审，提前半小时提醒我，再问问小梅能不能陪我去。”

预设 AI 错误：把“上午九点”识别为“上午八点”，使提醒时间先显示为 7:30；老人改回 9:00 后，提醒同步更新为 8:30。

演示分支：

1. 老人把误识别的 8:00 修改为 9:00，确认事务和 8:30 提醒；
2. 老人确认只向小梅分享事项、日期、时间、地点和“希望陪同”；
3. 小梅接受，老人看到明确结果；
4. 重置后演示老人撤回陪同请求，但保留自己的事务和提醒；
5. 重置后演示小梅尚未回应；
6. 重置后演示发送失败和重试。

## 5. 页面与状态清单字段

每一项必须包含：

- 编号；
- 页面/弹窗/状态名称；
- 使用角色；
- 进入方式；
- 前置状态；
- 展示信息；
- 主要与次要操作；
- 操作后的状态和去向；
- Web 路由或触发方式；
- 静态原型文件位置；
- 对应验收步骤。

## 6. 走查用例

### WT-01 主流程

首次建立关系 → 老人输入 → AI 确认 → 修改时间 → 创建事务 → 授权共享 → 家属接受 → 老人看到结果。

### WT-02 修改/取消

老人发送请求后取消 → 家属端显示已取消且不能继续回应 → 老人端结果一致。

### WT-03 失败/无法继续

AI 无法理解或请求发送失败 → 保留已输入内容 → 手动填写或重试 → 不显示假成功。

### WT-04 未回应

请求已送达但超时未回应 → 老人看到“暂未回应”及替代动作 → 家属端保持清楚状态。

## 7. 提交检查

- [ ] Docker 无网络、无密钥即可启动；
- [ ] README 写明访问、角色、案例、异常入口和重置；
- [ ] 无真实个人信息和凭据；
- [ ] 无空按钮、断路由和状态冲突；
- [ ] 已记录主流程、取消、失败和多角色走查；
- [ ] 最终 commit SHA 已在考核系统确认；
- [ ] 材料回执与最终 SHA 一致；
- [ ] 由候选人本人在网页确认交卷。
